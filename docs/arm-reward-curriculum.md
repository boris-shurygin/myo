# Поэтапная награда для руки: точность, затем экономия

Продолжение [разбора награды E15](arm-load-orientation-efficiency.md#e15-может-ли-экономия-усилий-компенсировать-ошибку-положения).
Согласованный первый опыт — обучение только на точности; условное включение
остальных слагаемых возле цели пока не смешиваем с этой проверкой.

## План до запуска

Две последовательные ветки из одного `hold_joint_corrective/best.zip` E10:
`native` сохраняет текущую награду, `position_only` оставляет прежнее
позиционное слагаемое и штраф physical failure. Множитель0,1,физика,40-ms
моторная задержка,активация,упругость,начальная capacity1,trigger1 и действия
совпадают. Поощрение малой скорости и **все** штрафы усилий/контакта/нагрузок
в position-only не участвуют; физический контакт продолжает действовать.
Это пакетная абляция дополнительных слагаемых,не изоляция одного speed term.

В обеих ветках одинаково локализуем расписание на сложной области:
цели120/135°,старты с offsets0/+10° в диапазоне15…135° (три пары),наклоны
120/150°,массы0,5/1/2 kg,4 s:18 учебных условий. Поэтому сравнение нового
варианта только с исторической E10 недостаточно — запускается matched native.
Одинаковые actor/critic и RMSprop moments,LR1e−5,4 среды×256,seed0,
те же PPO/архитектура/наблюдения. Изменение награды требует переобучения
критика; его начальное смещение и статистики PPO сохраняются в истории.
Это проверка снятия дополнительных terms у уже обученной policy с известным
ошибочным режимом. Она не эквивалентна обучению с нуля на position-only:
отрицательный результат не исключит,что новая reward помогла бы сформировать
другой навык с другой инициализации или в отдельном mass-curriculum.

Validation27:пары125→125,130→130,135→125°;наклоны115/135/155°;
массы0,75/1,5/2 kg. Ни один такой наклон/целевая пара не входит в локальный
train. Проверяем также все18 учебных условий,чтобы отличать освоение от переноса.
Заранее отложенный test8:hold122/132°×tilt125/145°×массы1/2 kg.
Он не используется для выбора checkpoint или решения о длительности обучения.
Это новое локальное сравнение; прежний общий test72 не объявляется новым holdout.

Первый одинаковый бюджет65536 переходов на ветку,validation каждые16384.
Дальнейшее продолжение оправдано наблюдаемым прогрессом; отсутствие прогресса
на двух блоках32768 считается плато. Один блок не доказывает невозможность
обучения. Выбор best — число pass,затем tail RMSE,при0 physical failures.
Для перехода к экономизации нужны18/18 учебных условий и≥90% validation,
с контролем каждой группы массы/наклона. Pass прежний:≥90% последней секунды
с ошибкой≤3° и скоростью≤5°/s; проверка одних RMSE не заменяет этот критерий.

Экономизация — только после этой проверки. Награда за точность сохраняется,
добавляемые activation-costs повышаются отдельными фазами; checkpoint должен
сохранять точность/число pass до сравнения экономии. `position_efficiency`
предусмотрен отдельным контрактом,но наличие режима не означает проведённого
обучения второй стадии. Вначале не добавляем predictor,демонстрации или новые
сенсоры. Старые source hashes/загрузчики не ослабляем.

На ноутбуке одновременно один тяжёлый процесс:CPU12–15,nice19,ionice idle,
один поток Torch/BLAS. Все веса/rollouts остаются в ignored `runs/`.
В процессе native-пилота внешней проверкой `/proc` подтверждены CPU12–15
иnice19 у всех10 собственных процессов. Пул проверки удерживал около2,5 GiB
RSS между замерами. Для следующего запуска runner получил
`--evaluation-workers 2 --release-evaluation-workers`:пул освобождается после
замера. Это только управление ресурсами независимой deterministic evaluation;
число учебных сред4 и PPO не меняются. Начальные validation-результаты ветвей
должны совпасть побитово,несмотря на разбиение evaluation на два/четыре процесса.

## Реализация и проверки

Новый wrapper `src/myo/arm_reward_curriculum.py`,отдельный schema
`myo.arm_reward_curriculum.v1`:reward stage,порядок входов,физическая
конфигурация и SHA исходников проверяются при загрузке. Изменены только
runner и маршрутизация evaluation; pinned workload/precision/actor-код сохранён.
Evaluation использует общую native-физику и прежние критерии качества,
независимо от учебной награды. Нативная reward-ветка побитово сохраняет награду
исходного wrapper на одинаковых действиях.

Команда regression:

```bash
nice -n 19 ionice -c 3 taskset -c 12-15 env \
  OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  .venv/bin/python3 -m pytest -q tests/test_arm_reward_curriculum.py tests/test_arm_workload.py
```

Результат:6 passed in5,00 s. Проверены одинаковые физические/мышечные состояния,
изменение только reward,сохранение termination penalty и несовместимость
checkpoint с подменённой наградой. Это проверка реализации,не успех policy.

## Команды запуска

Первый position-only pilot (validation manifest зафиксирован до обучения):

```bash
nice -n 19 ionice -c 3 taskset -c 12-15 env \
  OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  .venv/bin/python3 scripts/train_arm_workload.py \
  --stage hold_circle --root runs/arm_reward_curriculum/position_only \
  --parent runs/arm_workload/hold_joint_corrective/best.zip \
  --workers 4 --evaluation-workers 2 --release-evaluation-workers \
  --lr 1e-5 --minimum-steps 65536 --fixed-steps 65536 --check-steps 16384 \
  --masses 0.5 1 2 --tilts 120 150 --hold-targets 120 135 --hold-start-offsets 0 10 \
  --validation-file runs/arm_reward_curriculum/validation.json --reward-mode position_only
```

Native-пилот использовал тот же parent/spec/budget и `--reward-mode native`,
root `native`,без двух новых resource-флагов evaluation. В continuation root
`position_continuation`,parent `position_only/last.zip`,минимум32768 и нет
`--fixed-steps`. Сохранённые roots не перезаписываются; для повторов нужны новые
пути. Фактический runner source и SHA/spec/manifest сохранены в каждом root.

### Проверка выхода из контактной позы

Для selected best продолжения выполнены три native-прогона при цели125°,
tilt135°,2 кг. До2 с команды выдаёт одна и та же сеть. Полные мышечные состояния,
q/qvel и наблюдения в момент переключения имеют одинаковый SHA256.
После2 с состояние не перезаписывается: новые команды проходят настоящую
40-ms очередь, активацию и упругие сухожилия.

Моменты в позе переключения, по силам/плечам на конце интервала:
сгибатели+0,048 Н·м, разгибатели−6,667 Н·м, требуемый для равновесия
компенсирующий bias-момент−9,159 Н·м,
constraint torque−2,538 Н·м. Суммарную недостающую поддержку обеспечивает контакт.
Сильного активного взаимного сопротивления в этом ошибочном режиме не видно.
Активации трёх разгибателей при этом около0,808/0,389/0,689: даже сильная
активация одного пучка не равна полному доступному разгибающему моменту.

Отдельные фиксированные позы подтверждают падение доступного момента глубоко
в сгибании. Native-мышцы после1,2 с команды максимального разгибания:
при125° около−18,05 Н·м против требуемых−9,27; при143° около−9,45 против−9,14.
Это не точная мгновенная граница: начальная capacity1, в конце около0,9896,
утомление не выключалось. Прямой динамический прогон выше подтверждает саму
возможность выхода. Запас возле контакта мал, и нужна длительная сильная
команда; одного запаса в целевой позе недостаточно для объяснения возврата.

На успешном условии125°/tilt135°/1,5 кг аудит целых4 с дал native-discounted
return7,176 у поздней position-only против4,965 у matched native. При этом
tail RMSE0,381° против17,238°. Значит, более точная траектория выгоднее и по
старой награде с её штрафами. Это deterministic rollout, не независимая
калибровка critic и не сравнение ожидаемых returns стохастических policy.

Следующая проверяемая гипотеза — трудность обнаружения/закрепления достаточно
длительного сильного возбуждения для выхода из контакта. Возможные отдельные
опыты: временная структура исследования или curriculum масс/начальных
отклонений. Здесь они не проводились; причинный механизм PPO не установлен.

### Почему на снимках сеть сильнее активирует мышцу, но не удерживает цель

Для галереи `runs/problem_poses/README.md` повторены три пары реальных прогонов
по 4 с; углы/активации совпали с manifest снимков. HUD показывает одну мышцу,
однако обе policy и эвристика управляют всеми шестью. В первом примере
активации трёх головок трицепса сети — 80,9/39,0/68,9%, эвристики —
45,1/45,1/45,1%. В старом E8 при цели 30° сеть активирует BIClong/BICshort/BRA
на 44,6/43,4/29,9%, эвристика — на 30,3/30,3/30,3%.

Сравниваются разные достигнутые позы: изменившийся механический рычаг
снижает момент даже при большей силе сухожилия выбранной мышцы.

| Состояние на 4 с | Угол | Выбранная мышца | Сила | Плечо силы | Момент, модуль |
| --- | ---: | --- | ---: | ---: | ---: |
| Цель 125°, tilt135°, сеть | 142,48° | TRIlong | 555,92 Н | 4,61 мм | 2,57 Н·м |
| Те же условия, эвристика | 125,02° | TRIlong | 330,48 Н | 8,72 мм | 2,88 Н·м |
| Цель 30°, tilt45°, сеть E8 | 20,52° | BIClong | 274,16 Н | 10,25 мм | 2,81 Н·м |
| Те же условия, эвристика | 29,99° | BIClong | 195,38 Н | 15,09 мм | 2,95 Н·м |

В первом провале все разгибатели дают 6,60 Н·м против требуемых 9,16 Н·м;
сгибатели сопротивляются на 0,05 Н·м, контакт добавляет 2,61 Н·м разгибания.
В E8 сгибатели дают 7,60 Н·м, трицепс сопротивляется на 0,12 Н·м, пассивный
ограничитель добавляет 1,22 Н·м сгибания против требуемых 8,70 Н·м.
Это ошибочные равновесия с поддержкой пассивной механики, а не отсутствие
подключения остальных мышц. Выход в целевую позу и удержание в ней — разные
режимы: в первом примере эвристика ранее достигала 97,9% активации трицепсов.
Числа характеризуют текущую геометрию/динамику модели, не доказанную анатомию.

Полный разбор всех шести мышц и trace: `runs/problem_poses/muscle_forces.json`;
повторяемый диагностический source: `runs/problem_poses/inspect_forces.py`.

### Эвристика из тех же состояний и роль антагонистов

На тех же трёх screenshot-состояниях на 4 с переключены только команды на
эвристику. Сохранены скорость, моторная очередь, активации, упругие состояния
и capacity. Горизонт завершения продлён до 6 с; совпадение наблюдавшихся
физических величин с исходными кадрами до переключения проверено с допуском
1e−10. Все три native-прогона вышли в исходную целевую полосу ±1° через
0,64/0,70/0,94 с, закончили на 124,973/119,971/29,923° без physical failures.
Попадание в полосу не объявляется временем установления. Первая команда
эвристики в двух глубоких сгибаниях — все три разгибателя 100%, сгибатели 0;
в E8 при 20,52° — все три сгибателя 42,23%, разгибатели 0.

### Выходная функция и доступность сильных команд

В текущей policy скрытые слои используют SiLU. Последний `Linear(128,12)`
выдаёт по два числа на мышцу: `alpha=softplus(z_a)+0.05`,
`beta=softplus(z_b)+0.05`. Во время PPO исполняются независимые Beta samples,
в deterministic demo — среднее `alpha/(alpha+beta)`. Это excitation до
моторной задержки, не мгновенная активация мышцы. Tanh squashing отсутствует.

Для конечных положительных alpha/beta среднее строго между 0 и 1; точные
границы не представлены математически (численное округление отдельно).
Жёсткого потолка 80–85% нет: alpha=5,beta≈0.05 даёт около99,01%,
alpha=50,beta≈0.05 —99,90%. Рост alpha не ограничен. При стремлении к границе
чувствительность среднего может снижаться; это свойство параметризации,
а не непосредственная формула PPO-градиента через среднее.

Параметры прочитаны из реальных состояний трёх screenshot-прогонов на 4 с.
Для первого (q142,48°,цель125°,tilt135°,груз2 кг):

| Мышца | Alpha | Beta | Средняя команда | STD | P(команда>95%) при данном состоянии |
| --- | ---: | ---: | ---: | ---: | ---: |
| TRIlong | 22,023 | 5,193 | 80,92% | 7,40 п.п. | 0,643% |
| TRIlat | 12,229 | 19,166 | 38,95% | 8,57 п.п. | 4,94e−18 |
| TRImed | 24,274 | 10,974 | 68,87% | 7,69 п.п. | 5,50e−7 |

У этих выходов beta далеко от floor0,05; raw logits положительны, производная
Softplus близка к1. То есть насыщение Softplus не объясняет остановку этих
команд. Производные среднего по raw alpha равны0,0070/0,0194/0,0088,
по raw beta —−0,0296/−0,0124/−0,0195: они конечны и не обнулились.
Эти числа — локальная чувствительность среднего, не измерение PPO policy loss:
PPO дифференцирует log_prob исполненных действий.

Измеренная policy уже узко исследует окрестности недостаточных команд.
Особенно сильные команды TRIlat в этом состоянии практически не встречаются;
это поддерживает гипотезу недостаточного исследования сильного совместного
усилия. Но оценка **конечного checkpoint при фиксированном состоянии** не
доказывает, что такие команды не встречались раньше во время обучения.
Аналогично в E8 BRA:mean29,92%,STD5,25 п.п., хотя эвристика из того же состояния
выдаёт42,23%; переход к этому значению требует умеренного сдвига, не максимума.
Поэтому одна недоступность100% не объясняет все три провала.

Вероятности хвостов вычислены интегрированием Beta density (96-node
Gauss–Legendre, сверка192 nodes). Monte Carlo100000 samples также сохранён;
нулевое число попаданий в нём не объявляется нулевой вероятностью.
Source/параметры/чувствительности: `runs/problem_poses/inspect_output_head.py`
и `output_head.json`. Изменения output head и новые обучения здесь не делались.
Возможный следующий отдельный опыт — параметризовать среднее и концентрацию
раздельно, сохранив физику, reward, сценарии и matched PPO budget; доступ к
сильным командам оценивать вместе с pass/RMSE, а не только увеличением шума.

### Сопоставление выходов с MuscleMimic

Проверены сохранённые первичные исходники commit
`47b653db2bce25de834360d2ee6b2dd88142bd78` и [статья v1](https://arxiv.org/html/2603.25544v1#S5.SS4).
В [ActorCritic/networks.py](https://github.com/amathislab/musclemimic/blob/47b653db2bce25de834360d2ee6b2dd88142bd78/musclemimic/algorithms/common/networks.py#L166)
последний слой среднего линейный (`output_activation=None`), распределение
диагональное нормальное: `a=mu(s)+exp(log_std)*epsilon`. `log_std` — обучаемый
вектор на мышцы, не выход сети, зависящий от состояния. Скрытые слои — SiLU.
В [DefaultControl/direct](https://github.com/amathislab/musclemimic/blob/47b653db2bce25de834360d2ee6b2dd88142bd78/loco_mujoco/core/control_functions/default.py#L77)
для actuator range[0,1] исполняется `u=clip((a+1)/2,0,1)`.

Следствие: конечное raw action `a>=1` даёт ровно100% возбуждения, `a<=-1` —0%.
В deterministic-режиме это относится к среднему raw action; в stochastic —
к Gaussian sample. PPO обучается через log_prob raw Gaussian action, поэтому
нулевая производная clipping по a не является автоматическим обнулением
PPO-градиента. У clipping есть и недостаток: разные raw действия могут
исполняться одинаково; это не доказательство превосходства Gaussian над Beta.

Настройки noise различаются: в pinned bimanual config `init_std=0.2`,
`learnable_std=true`, `ent_coef=0`; в статье Appendix D для full-body
`init_std=3.0`, для bimanual0.2. Это **raw action units**, не STD готового
возбуждения: линейный mapping до clipping делит масштаб пополам. При mean0
и STD3 нормальное распределение отправляет около36,9% samples на u=1 и
столько же на u=0 (расчёт из Gaussian CDF и mapping, не измерение их rollout).
В Appendix A авторы сравнивают STD0.2 с3.0: на стандартных KINESIS движениях
эффект невелик; важность большого начального шума для динамичных движений
приводят как эмпирическое наблюдение, не универсально доказанный результат.

Ещё одно отличие инициализации: маленькие начальные веса linear mean и нулевой
bias дают raw mean около0, то есть excitation около50% до clipping; наша Beta
head начинает со среднего около10%. Поэтому перенос одного Gaussian head
без контроля начального среднего/разброса смешает несколько изменений.
Сопоставление не является новым опытом обучения: параметры policy и физики
не менялись. Подробнее о прежнем переносе методики — [vertical-musclemimic.md](vertical-musclemimic.md).
