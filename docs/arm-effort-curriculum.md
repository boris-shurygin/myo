## Что проверяем

Можно ли после освоения позиции уменьшить фактическую активацию мышц,
сохранив точность? Малые затраты при провале цели не считаются экономией.
Мера`mean(a²)` —proxy усилия,не механическая работа/метаболические джоули.
Отдельно сохраняем`mean(a*capacity)`,capacity,активации антагонистов и движения.
У parent антагонисты уже относительно слабы:средняя tail coactivation по
условиям validation около0,023. Не предполагаем заранее большой резерв.

Первый парный опыт —две последовательные ветви от одного parent:

| Ветка | Награда |
| --- | --- |
| Control | `0.1 * (position_log + physical_failure)` |
| Activation0.1 | `0.1 * (position_log + physical_failure - 0.1*mean(a²))` |

Используем существующий `position_efficiency` contract в обеих ветвях,
с coefficient0/0,1. Награда за точность прежняя,нового переключателя у цели
не добавляем;это вторая фаза curriculum. Затраты вычисляются по реальной
активации после очереди/фильтрации,не по только что выданному возбуждению.
Active-fraction/fatigue weight0. Отдельный штраф за утомление пока не смешиваем
с первым опытом по квадрату активации. Все физические параметры неизменны.

PPO/architecture/наблюдения/detector прежние:actor/critic4×128 SiLU,
RMSprop,LR1e−5,4×256,10 epochs,batch128,gamma0,99,GAE0,95,
clip0,2,entropy0,001,KL0,03,temperature≤16. Predictor отсутствует.
Одни seed0/условия,одинаковые policy tensors/RMSprop moments в начале.
Физические состояния/RNG перезапускаются один раз в начале каждой ветви.

Фиксированный matched бюджет **65536 переходов на ветвь**,assessment каждые
16384. Сначала Control,затем Activation0.1;одновременно один тяжёлый job.
CPU12–15,nice19,ionice idle,Torch/BLAS по одному потоку. Не меняем
веса/ориентации/4-s эпизоды и18 train/27 validation/8 test условий.

## Отбор и оценка

Начальный parent —допустимый checkpoint,поэтому в худшем случае сохраняется
он. Для eligibility нужны все18 train и все27 validation pass,failures0,
mean tail RMSE каждого набора≤начальной+0,25°. Среди допустимых выбираем
минимальное среднее`mean(a²)` с равным весом train/validation;затем точность.
Выбор не использует test. Обе ветви используют один и тот же отбор.

Сравниваем выбранные best,а также last и исходный parent. Число обновлений
и KL-остановки записываем:равное число transitions не означает равное SGD.
Цель первого опыта —снижение proxy хотя бы10% к parent и5% к matched control
при сохранении pass;при меньшем эффекте показываем числа без объявления
цели достигнутой. Отдельный test оценивается после фиксации выбранных файлов;
известный test прошлых опытов не становится новым holdout.
На test сохранение качества также означает все8 pass,failures0 и
mean tail RMSE≤parent+0,25°. Это оценка выбранного по train/validation
checkpoint,не дополнительный выбор по test.
Проверяем full-episode затраты и tail активации/ошибки,чтобы не выдать
расслабление в начале с медленным восстановлением за улучшение удержания.

Если coefficient0,1 не даёт эффекта или есть прогресс к концу бюджета,
следующая отдельная фаза может увеличить бюджет/коэффициент. Это решение
принимается по train/validation,не по test. Если точность ухудшается,
parent сохраняется;проверяем меньший штраф/LR прежде усложнения архитектуры.

отсутствие допустимой экономии,следующая отдельная пара начинает **от того же
успешного parent**,меняя только LR на3e−6. Коэффициенты0/0,1 сохраняются;
по32768 переходов на ветвь,check каждые16384,тот же отбор и seed.
Это проверка стабильности небольших PPO-обновлений,не смена награды/физики.

### Почему одного среднего RMSE недостаточно

`scripts/diagnose_arm_effort.py` отдельно воспроизводит три известных трудных
удержания,по4 s,mean-команды,неизменная native механика. Это диагностические
пробы по train/validation,не новый test и не дополнительный отбор policy.
Показаны RMS скорости и доля последней секунды со скоростью≤5°/s:

| Policy | Hold135°,tilt150°:RMSE | RMS скорости | Доля приемлемой скорости |
| --- | ---: | ---: | ---: |
| Parent | 0,088° | 0,779°/s | 1,000 |
| Control,LR1e−5,last | 0,975° | 7,665°/s | 0,333 |
| Activation0.1,LR1e−5,last | 0,977° | 0,908°/s | 1,000 |
| Control,LR3e−6,last | 1,014° | 9,351°/s | 0,275 |
| Activation0.1,LR3e−6,last | 0,843° | 7,180°/s | 0,333 |

У всех этих проб ошибка положения укладывалась в3° на всех tail-отсчётах.
Провалы control —именно скорость/колебания. На Hold130°,tilt135° control
LR1e−5 также имел position fraction1,0,но speed fraction0,373.
При этом Activation0.1 LR1e−5 в Hold135°,tilt120° держит неверное равновесие:
ошибка5,363°,RMS скорости0,254°/s,position fraction0. У parent там2,442°
и settled fraction0,980. Пробы младшего LR удерживают положения в3°,
но недостаточно спокойны. Физических срывов нет.

Есть конкретное несовпадение цели и приёмки:reward этой фазы оценивает
положение и активацию,а pass требует также малую скорость. Дальнейшее
улучшение среднего position RMSE совместимо с потерей стабильного удержания.
Это проверенный симптом,не доказательство единственной причины неудачи PPO.
Более сильный штраф/ещё меньший LR без проверки скорости пока не оправдан.
Следующий осмысленный опыт —согласовать награду со спокойным удержанием
вблизи цели,сначала проверить позиционный контроль,затем снова экономию.
В этом опыте такую новую награду не вводили.
