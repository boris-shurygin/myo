## Измеренная механика и постановка

В MyoArm уже есть масса сегментов: подвижное поддерево локтя с грузом1 kg
весит2,783386 kg, следовательно предплечье/кисть без груза —**1,783386 kg**.
Humerus1,99757 kg закреплён; его вес не добавляет момента вокруг локтя.
Это параметры импортированного стенда, не измерения конкретного человека.

Поворот плеча здесь означает поворот **всего закреплённого стенда** вокруг
той же оси, которая меняет направление гравитации в плоскости локтя.
Покрываем0…360° периодически, без дублирования0° и360° в train.
Менять ориентацию/массу разрешено только при reset; нагрузка не подстраивается
для спасения policy. Внутри эпизода сохранены MuJoCo, физика1 ms, управление20 ms,
transport40 ms, activation15/50 ms, независимое упругое сухожилие и fatigue proxy.

Нативная масса груза уже входит в153 наблюдения. Добавляем две причинные
координаты: sin(tilt)−sin30° и cos(tilt)−cos30°. При исходных30° они нулевые.
Вход становится155; первые153 каналов, история и FIFO не переупорядочиваются.
Начальные private слои расширяются двумя нулевыми колонками; их RMSprop moments
тоже нулевые. Остальные веса/moments переносятся точно.
Старые core/contracts не меняются, новый протокол имеет отдельный strict loader.

## Порядок опытов

1. **Аудит до обучения.** Статическая достижимость требуемых моментов при разных
   позах/ориентациях/грузах, baseline поведения и фактической активности трицепса.
   Разделяем активную команду/активацию и пассивную силу сухожилия. Проверяем,
   что наблюдения различают ориентации и что полный оборот возвращает ту же физику.
2. **Масса при30°.** Train0,5/1/2 kg, прежние27 задания. Контроль — обучение
   только1 kg из того же parent при одинаковом опыте. Validation9 прежних пар×3
   массы; final test11 пар×0,75/1,5/2,5 kg (последняя — экстраполяция).
3. **Ориентации.** Начинаем с удержаний30/60/90/120°, затем добавляем перемещения.
   Сначала0/30/60°, затем расширяем до12 направлений с шагом30° на полном круге.
   Груз1 kg на первом круговом этапе; затем возвращаем0,5/1/2 kg совместно.
   Validation включает промежуточные углы стенда; final test — отдельные offsets.
4. **Экономичность.** Из общего обученного parent сравниваем исходную reward,
   добавку за квадрат активации и затем дополнительную стоимость active fraction
   `activation*capacity` как proxy интенсивности утомления. Коэффициенты меняются
   по одному; не штрафуем конкретно трицепс и не поощряем конкретную синергию.
   Остальные направления должны сами изменить роли антагонистов при смене гравитации.
5. **Сниженная capacity и удержания.** Train начальная capacity1/0,7; проверка
   промежуточной0,85 и20-s удержаний. Утомление развивается по существующему закону;
   не ускоряем его ради награды. Отчёт — точность, активации, gross fatigue proxy
   и реальные изменения capacity, а не только суммарная reward.

## Метрики и правила продолжения

Угловая точность/скорость/overshoot/время установления, число physical failures,
pass (90% последней секунды с |ошибкой|≤3° и |скоростью|≤5°/s), отдельные группы
по массе/ориентации/направлению движения и capacity.
Дополнительно mean activation, mean activation², активность обеих групп,
coactivation proxy `min(mean flexor activation, mean extensor activation)`,
time-integrals proxy-затрат и падение capacity по каждой мышце.
Снижение затрат с потерей удержания не считается улучшением.
Механическая работа сама по себе недостаточна: при изометрическом удержании
она близка к нулю, хотя активация и fatigue proxy остаются ненулевыми.
Без метаболической модели не называем эти числа джоулями расхода организма.

PPO: прежние Beta excitations, RMSprop, LR3e−5, gamma0,99, GAE0,95, clip0,2,
entropy0,001, vf0,5, grad-norm0,5, target-KL0,03. Проверяем4 CPU-среды×256
шагов = прежние1024 transitions на rollout; batch128 и10 epochs сохранены.
Это явно новый sampling-режим; контроль массы использует тот же режим.
Среды получают разные части одного фиксированного расписания условий, seed0.
Оценка выполняется в независимой среде и не расходует RNG обучения.

Проверки блоками16384, продолжение по32768 transitions. Стартовые условия,
каждый checkpoint, реальные SGD/KL-stop, validation и seed записываются.
Продолжаем, пока есть накопленный прогресс: дополнительные pass без роста
failures либо снижение mean/worst-group ошибки≥2%. Два полных блока без
такого прогресса — основание диагностировать текущую схему, а не бесконечно
наращивать тот же бюджет. Если есть прогресс, очередная граница бюджета
не считается завершением исследования.

Масса/ориентации: практический проход этапа≥90% validation без failures,
не менее75% в каждой группе и средняя tail RMSE≤3°.
Экономичность: сохраняем tracking-best и Pareto-кандидаты; уменьшение затрат
при ухудшении средней ошибки более чем на0,25° или потере pass фиксируем как
компромисс, а не успех. Final test открывается после фиксации выбора,
не управляет продолжением. Один seed; статистическая устойчивость не заявляется.

Набор33 mass-test общий для последовательных веток. После открытия в E2 он
служит повторяемой регрессионной проверкой: поздние результаты на нём не
являются новым слепым test всей исследовательской серии. Выбор checkpoint
внутри каждой ветки по-прежнему делается только по её validation и фиксируется
до replay/test. Аналогично явно отделяем20-s удержания от4-s обучения.

Если этап застрянет, проверяем доступность момента, состояния при reset,
сигнал ориентации, покрытие условий, stochastic/mean разрыв и KL/moments.
Затем пробуем обоснованные изменения по одному: темп curriculum, LR,
баланс удержаний/перемещений, начальные физически реализуемые состояния.
Нельзя добавлять мгновенный joint torque, обнулять скорость, убирать задержку
или менять нагрузку для спасения rollout. Окончательный отчёт объяснит,
какой этап пройден и где закончились обоснованные варианты продолжения.

По вопросу владельца сопоставлены сохранённые tail-активации E8/E10.
Взаимная активная тяга действительно может уменьшать результирующий момент
и повышать затраты. Однако в самых грубых провалах mean-команд антагонисты
к концу эпизода почти расслаблены. Для E10 best,среднее за последнюю секунду
по трём мышцам каждой группы:

| Цель локтя / наклон / масса | Сгибатели, % активации | Разгибатели, % активации | Tail RMSE, ° |
| --- | ---: | ---: | ---: |
| 125° / 135° / 2 kg | 0,13 | 44,72 | 17,88 |
| 120° / 165° / 2 kg | 0,12 | 46,80 | 22,12 |
| 30° / 45° / 2 kg | 38,48 | 0,32 | 10,26 |

Это активации в фактически достигнутых позах, не необходимые активации
в целевых положениях. Активация не равна силе: пассивное натяжение мышц,
состояние сухожилий и плечи моментов нельзя восстановить одним усреднением.
По этим данным нельзя полностью исключить сопротивление пассивных тканей
или влияние коактивации в переходном процессе.

Но сохранённая native-проба E8 при125°/tilt135°/2 kg показывает и недостаток
торможения во время движения:на0,1 s mean активации сгибателей/разгибателей
0,0311/0,3544,на0,2 s —0,0058/0,4623. Эвристика на тех же временах даёт
0,0090/0,5987 и0,0012/0,9653 и затем возвращается к цели. Проба с правильным
начальным preload также проваливается (E10 журнала). Поэтому объяснение
«весь полезный запас съеден постоянной сильной активацией обеих групп»
не подтверждается для основных контактных провалов. Лишняя коактивация
остаётся отдельной задачей эффективности,а нехватка выданного торможения —
более прямой наблюдаемый признак текущего провала. Причина обучения ещё
не установлена. Следующая причинная проверка потребует измерить отдельные
моменты/силы групп и кратко подавить антагонистические команды через обычные
задержку/активацию; такая абляция текущих E8/E10 здесь не проводилась.

### E15. Может ли экономия усилий компенсировать ошибку положения?

Проверены reward-formula,сохранённые spec E8/E10 и разложение native-пробы
E8 при125°/tilt135°/2 kg. Дополнительные weights `activation_squared_weight`
и `active_fraction_weight` у обеих фаз равны0:парный efficiency-опыт E7
не переносит свои новые штрафы в эти фазы. При этом прежние native-штрафы
возбуждений,их изменения,capacity-loss proxy и суммарной силы сухожилий
продолжают действовать.

Средние слагаемые за последнюю секунду cold-start пробы,до общего multiplier0,1:

| Слагаемое | Learned E8, ошибка17,907° | Heuristic, ошибка0,01389° |
| --- | ---: | ---: |
| Положение | +0,546225 | +0,849280 |
| Покой / малая скорость | +0,150000 | +0,150000 |
| Квадрат возбуждения | −0,001017 | −0,001012 |
| Суммарная сила сухожилий, proxy | −0,067731 | −0,059540 |
| Контактная сила, proxy | −0,035342 | 0 |
| Вся награда после multiplier | **0,059201** | **0,093866** |

Оставшиеся малые terms включены в итог. В этом устойчивом ошибочном режиме
нет компенсации потери точности экономией возбуждений; суммарный force-cost
тоже хуже,чем у точного управления. Полностью сбалансированный reset даёт
то же ранжирование0,059279 против0,093857. Это сравнение tail-наград двух
контроллеров,не доказательство глобального оптимума и не сравнение полных
дисконтированных returns.

Отдельная проблема возможна **на пути к лучшему положению**. Для удержания
целевая скорость0,и term `.15*exp(-(qvel/1.5)^2)` максимален при покое даже
в неверной позе. Иллюстрация самой формулы (не физический прогон): при
уменьшении ошибки18→17° positional gain+0,007634,но переход от покоя к50°/s
даёт velocity loss−0,043070. Без остальных terms мгновенная награда ниже,
хотя ошибка уменьшилась. На реальной траектории добавляются задержка команд,
активация,пики сил и smoothness-cost; последующий выигрыш должен быть отнесён
к действию через returns/critic/GAE. Поэтому локальный барьер обучения возможен
даже при явно лучшей награде правильного конечного состояния. Общий
multiplier0,1 сам по себе не меняет соотношения слагаемых.

Чистые следующие проверки (ещё не выполнены): matched продолжения с отдельно
выключенными effort/fatigue terms,отдельно force-proxy penalty и отдельно
уменьшенным velocity term. Не менять их одновременно. Сравнить полный
discounted return/разложение по времени,возврат из отклонения и локальные
advantages в сложных учебных ячейках E11. Teacher остаётся диагностикой;
его точность сама по себе не доказывает верное ранжирование sampled-действий
критиком. Локальная JSON-сводка:`runs/arm_workload/reward_balance_analysis.json`.

### E16. Поэтапная награда — завершённая первая проверка

## Ограничение нагрузки на ноутбук

Во время продолжения `hold_joint` его процессы и существующие
потоки были закреплены за четырьмя E-ядрами (логические CPU 12–15), CPU nice 19,
I/O class idle. Остальные 12 логических CPU доступны обычной работе.
К завершению E12 собственные training/evaluation-процессы закончились;
анализ E13 читает сохранённые JSON и не запускает обучение.
Одновременно запускаем только один тяжёлый опыт; дополнительные training,
evaluation и рендеры ждут его завершения. Физика и параметры PPO не менялись.
После завершения вспомогательных процессов доступная RAM выросла примерно
с 2,1 до 5,4 GiB; swap принудительно не очищался.

Для последующих запусков на этом ноутбуке команды ниже предваряем:

```bash
nice -n 19 ionice -c 3 taskset -c 12-15 env \
  OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  .venv/bin/python3 scripts/train_arm_workload.py ...
```

Это ограничение набора CPU и приоритета, а не жёсткий лимит температуры или ватт.

Для последовательной диагностики E8/E7 процессы основного опыта временно
останавливаются SIGSTOP и затем возобновляются SIGCONT в`finally` локального
runner. Это сохраняет среду, FIFO, веса/optimizer и RNG между блоками;
физическое время не продвигается в паузе. В отличие от прерванного E9,
нового warm-start/reset здесь нет. В памяти остаётся основная policy/пулы,
но CPU занимает только одна задача. Wall time E8 включает такие паузы и
не используется для сравнения скорости алгоритмов.

## Воспроизведение и артефакты

Команды ниже используют локальные parent-checkpoints. При повторе нужен новый
`--root`: существующий каталог runner не перезаписывает. Версии пакетов,
полная spec/validation, hashes, source родителя, реальные SGD/KL и actual runner
source сохраняются вместе с каждым запуском. Точного восстановления сред/RNG
между фазами нет; weights и RMSprop moments переносятся явно.

```bash
.venv/bin/python3 scripts/train_arm_workload.py --stage mass \
  --root runs/arm_workload/mass --minimum-steps 65536
.venv/bin/python3 scripts/train_arm_workload.py --stage mass \
  --root runs/arm_workload/mass_capacity --parent runs/arm_workload/mass/best.zip \
  --capacities .7 1 --validation-capacities .85 --minimum-steps 65536
.venv/bin/python3 scripts/train_arm_workload.py --stage hold_circle \
  --root runs/arm_workload/hold_circle_low_lr \
  --parent runs/arm_workload/hold_circle_resume/best.zip \
  --hold-targets 30 60 90 120 135 --lr .00001 --minimum-steps 32768
.venv/bin/python3 scripts/train_arm_workload.py --stage hold_circle \
  --root runs/arm_workload/hold_joint --parent runs/arm_workload/hold_circle_low_lr/best.zip \
  --hold-targets 30 60 90 120 135 --masses .5 1 2 \
  --validation-masses .75 1.5 2 --lr .00001 --minimum-steps 65536
.venv/bin/python3 scripts/train_arm_workload.py --stage mass \
  --root runs/arm_workload/fatigue_03 --parent runs/arm_workload/mass_capacity/best.zip \
  --workers 2 --capacities .7 1 --validation-capacities .85 --fatigue .3 --fixed-steps 65536
.venv/bin/python3 scripts/report_arm_workload.py
```

Контроль E7 отличается только отсутствием`--fatigue .3` и своим`--root`.
Веса/rollouts остаются ignored; репозиторий хранит код, план и численные отчёты.
Сборка Linux-демо и параметры массы/наклона —[arm-interactive-demo.md](arm-interactive-demo.md).
