# Исходный предиктор: увеличенный бюджет и меньший learning rate

Продолжение [подбора параметров](vertical-tuning.md), 2026-11-06.
Проверяется, объяснялся ли слабый результат меньших learning rate недостатком
обновлений. Это обучение предиктора вертикального стенда, не контроллера.

## Протокол

Все четыре исходные механики и прежние 12 эпизодов на механику сохранены.
Разделение целыми эпизодами: 6 train / 3 validation / 3 test, по 8 s.
Новых уникальных данных не добавлено. Истории ощущений и резервуара нет.
Входы — прежнее физическое состояние и действующая команда; очередь задержки
сдвигается аналитически. Нейронный переход 20 ms, BPTT — три перехода, 60 ms.

Сеть зафиксирована: 128×128, Tanh в скрытых слоях, линейный выход нормированных
приращений. Опыт не перенастраивает функции активации. Adam, batch 128,
clip L2 до 10, train-only нормировка, MSE всех физических каналов в единицах
STD одношагового приращения; seed 0, два torch-потока CPU. Scheduler отсутствует.
Версии: Python 3.12.16, PyTorch 2.15.0+cpu, NumPy 2.5.4, MuJoCo 3.17.0.

Бюджет увеличен **в 10 раз**: одношаговая подготовка 1000 → **10 000 updates**,
BPTT 2000 → **20 000**. Проверяются lr **0,001 / 0,0003 / 0,0001 / 0,00003**.
Исходный 0,001 получает тот же увеличенный бюджет, чтобы сравнение не приписало
весь эффект времени обучения уменьшению lr. Частота validation прежняя:
updates 0, 1, каждые 100 и последний. Исходная модель участвует в выборе best.

Это повтор обучения с теми же начальными весами, а не возобновление старого
optimizer: прежние checkpoints хранят только выбранные веса. На границе стадий
Adam и minibatch-генератор создаются заново, как в предыдущем опыте.

Сначала четыре lr подготовки сравниваются по среднему validation score всех
четырёх механик. Затем все четыре lr BPTT стартуют из одинаковой выбранной
подготовки своей механики. Оставлен контроль с парой lr 0,001/0,001 и длинным
бюджетом; если общая подготовка выбрана с другим lr, он обучается отдельно.
Критерии выбора прежние: нормированная RMSE скорости на 20 ms для подготовки,
средняя на 20/60 ms для BPTT. Test вычисляется после фиксации всех решений.
Это последовательный подбор общих lr, не перебор всех 16 пар и не отдельный
подбор lr для каждой механики. Числа критериев разных стадий между собой
не сравниваются как улучшение/ухудшение.

Для каждой траектории отдельно сохранён лучший score её короткого префикса
1000 или 2000 updates. Это позволяет сравнить бюджет при неизменном начальном
состоянии optimizer. Префикс подготовки дополнительно сопоставляется побитово
со старым журналом. Для BPTT новый выбранный родитель может отличаться от
старого, поэтому его префикс нельзя автоматически считать прежним запуском.
Одна подготовка теперь использует 1,28 млн выборок окон из 2400 разных;
один BPTT — 2,56 млн из 2388. Это повторные предъявления, не новые примеры.

Исходные модули физики, архитектуры, сериализации и короткого подбора не
изменяются. Новый entry point вызывает прежнюю функцию обучения и сохраняет
тот же строгий checkpoint-контракт. Путь результатов — `runs/vertical_budget/`.

```bash
.venv/bin/python3 scripts/train_vertical_budget.py > runs/vertical_budget.log 2>&1
.venv/bin/python3 scripts/evaluate_vertical_tuning.py --run runs/vertical_budget
PYTHONPATH=/tmp/myo-supervised-plot-deps MPLCONFIGDIR=/tmp/myo-supervised-mpl .venv/bin/python3 scripts/plot_vertical_budget.py
```

## Одношаговая подготовка

Средний best validation score четырёх механик; меньше лучше. Короткий префикс
содержит те же первые 1000 updates, что прежний опыт.

| Learning rate | 1000 updates | 10 000 updates |
| --- | ---: | ---: |
| 0,001 | 0,62266 | **0,55253** |
| 0,0003 | 0,66310 | 0,55872 |
| 0,0001 | 0,86368 | 0,61671 |
| 0,00003 | 0,91656 | 0,65184 |

Дополнительное время действительно помогает малым lr; однако на общем
критерии 0,001 по-прежнему лучше. В полной механике его лучший update
переместился с 400 на 6100, score уменьшился 0,56513 → 0,49958. У механики 3
лучшим осталось обновление 200: более длительная подгонка не улучшила
validation. Поэтому одинакового оптимального числа обновлений для всех
механик здесь нет.

## BPTT и влияние бюджета

Все четыре lr BPTT стартовали из подготовки с lr 0,001. Средний best
validation score на 20/60 ms:

| Learning rate | Первые 2000 updates | Все 20 000 updates | Лучшие updates механик 1 / 2 / 3 / 4 |
| --- | ---: | ---: | --- |
| 0,001 | 0,94360 | 0,86934 | 8500 / 0 / 6000 / 0 |
| 0,0003 | 0,94014 | **0,86834** | 0 / 0 / 15500 / 0 |
| 0,0001 | 0,94173 | 0,88630 | 0 / 0 / 20000 / 0 |
| 0,00003 | 0,94190 | 0,94190 | 0 / 0 / 300 / 0 |

Выбрана общая пара **0,001 / 0,0003**. По сравнению с длинным контролем
0,001/0,001 преимущество всего **0,114%**. Это небольшой эффект одного seed
на одном фиксированном split, не установленное устойчивое превосходство lr.
При неизменном новом родителе увеличение бюджета BPTT с 2000 до 20 000
уменьшает score выбранного lr на **7,64%**. Совокупный результат относительно
прежнего короткого Tanh/linear контроля: **1,08144 → 0,86834**, на **19,70%**.
Последнее сравнение включает также более длительную подготовку.

Нулевой выбранный update означает, что сохранена **подготовка без BPTT**,
а не что BPTT не запускался. Все 20 000 updates выполнены. В выбранной общей
паре только механика 3 получает новые BPTT-веса. Её best найден на 15 500-м
обновлении: прежний лимит 2000 действительно скрывал полезное улучшение.
У lr 0,0001 для этой механики best на последнем update, поэтому плато не
установлено. Нельзя считать его большой итоговый score доказательством того,
что меньший lr вообще неспособен достичь хорошего результата.

В механиках 1, 2 и 4 BPTT при lr 0,0003 продолжает подгонять train, но
validation не улучшает. Например, в полной механике полная train MSE
трёхшагового состояния уменьшается **0,00460 → 0,00113**, а validation MSE
увеличивается **0,17676 → 0,24176**, velocity score **0,85222 → 0,99136**.
Это уже ухудшение на validation и полной MSE, не только несовпадение
velocity-критерия с loss. У lr 0,00003 ухудшение меньше, но улучшения нет.
Меньший шаг сглаживает часть колебаний, однако сам не решает обобщение.

## Test после фиксации выбора

Одинаковые 231 начало прогноза на 3 test-эпизодах. RMSE скорости, **mm/s**.
«Короткий» — Tanh/linear контроль предыдущего опыта, 1000/2000 updates.
Общий lr и updates не переназначались по test.

| Механика | Короткий, 20 ms | Длинный выбранный, 20 ms | Короткий, 60 ms | Длинный выбранный, 60 ms |
| --- | ---: | ---: | ---: | ---: |
| 1: без упругости и задержки | 0,503 | **0,240** | 0,695 | **0,488** |
| 2: упругость | 0,583 | **0,553** | 0,854 | **0,606** |
| 3: также задержка | 1,498 | **0,260** | 5,999 | **0,522** |
| 4: также постепенная активация | 1,046 | **0,375** | 2,795 | **0,630** |

На test выигрыш относительно короткого нового контроля есть у всех четырёх
механик. При прежнем lr 0,001 и том же длинном бюджете RMSE на 60 ms —
**0,563 / 0,606 / 0,566 / 0,630 mm/s**. Значит, основная часть улучшения
появляется и без снижения lr. В механиках 2/4 веса выбранного варианта и
длинного контроля совпадают: оба сохранили одношаговую подготовку.

В полной механике position RMSE через 60 ms — **0,0306 mm**.
С исторической моделью, обученной на BPTT 120 ms, выигрыш на 20/60 ms
также есть: её velocity RMSE **0,506 / 0,906**, теперь **0,375 / 0,630 mm/s**.
Однако через 400 ms новая ошибка **1,275** против исторической **1,005 mm/s**.
Улучшение ближнего прогноза не означает улучшения любого горизонта.

Validation всё ещё заметно труднее test: в полной механике RMSE 60 ms
для validation sine / steps / multisine — **1,665 / 5,289 / 1,729 mm/s**.
Первые 200 ms составляют 6 из 240 validation-окон и только 5,36% квадратичной
ошибки 60 ms. Проблема не объясняется одним холодным стартом. Split и test
уже использовались в прошлых исследованиях; это повторяемая диагностика,
не новая независимая выборка.

## Производные по командам

Дополнительно выполнен native replay и сравнение производной будущей скорости
по текущей команде: 6 состояний каждой механики, два мышечных канала, native
центральная разность ±0,005, последующие команды неизменны. Для задержанных
механик до 40 ms производная строго нулевая.

Метрика — `RMS(J_predicted - J_native) / RMS(J_native)` на 60 ms.
Это относительная ошибка Jacobian, не RMSE скорости из предыдущей таблицы.

| Механика | Прежний короткий контроль | Новый выбранный |
| --- | ---: | ---: |
| 1 | 0,1205 | **0,0941** |
| 2 | **0,0781** | 0,0870 |
| 3 | 0,9662 | **0,0724** |
| 4 | 0,6034 | **0,5247** |

У полной механики направление в проверенных точках в основном верное:
cosine **0,978**, значимые знаки совпали. Но относительная ошибка величины
отклика остаётся **52,5%**. У неё точность прогноза состояния заметно лучше
точности градиента для управления. Пригодность для обучения actor через
предиктор не установлена; эти 6 проб также не являются проверкой всей области
возможных команд и состояний.

## Артефакты и проверки

Обучение завершилось: **32 checkpoint**, **480 000 updates** суммарно,
**1036,65 s** на CPU с двумя torch-потоками. Все результаты в игнорируемом
`runs/vertical_budget/`, исходные веса не перезаписывались.

- `summary.json`: полный журнал, данные, источник runner, общие решения,
  короткие префиксы и test после фиксации выбора; status `complete`.
- `independent_evaluation.json`: строго загружены и перепроверены все 32
  checkpoint, нормировки, train/validation/test и решения; status `passed`.
  Native replay совпал с датасетом побитово; проверены 16 candidate Jacobian.
- `budget_comparison.json`: точное совпадение первых 1000 updates всех
  16 одношаговых ветвей со старым опытом, сравнение короткого/длинного бюджета.
- `budget_comparison`, `validation_curves`, `train_curves`, `test_comparison`:
  графики PNG/SVG экспортированы и просмотрены.

Regression-проверка существующего контракта и задержки — **4 passed**.
Полный набор повторно не запускался: изменения только в новых скриптах
оркестрации/графиков и документации; runtime физики, сети и сериализации
не менялся. Последний полный результат остаётся **125 passed** в предыдущем
опыте. Точные команды — в [validation.md](validation.md).
