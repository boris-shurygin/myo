# Runtime: ресурсы, время и граница Unreal

Дата решения и проверки источников: **2026-10-29**.
Это план исполнительной интеграции. В V0 нет UE-проекта или работающего
URLab-адаптера; скорость на целевом ПК ещё нужно измерить.

## Три разных расписания

| Процесс | Текущее значение V0 | Правило |
| --- | --- | --- |
| Механика и мышцы | `physics_dt = 0.001 s` | Фиксированный шаг симуляционного времени |
| Контроллер | `frame_skip = 20`, период `0.020 s` | Одна команда на 20 физических подшагов |
| Изображение UE | Ещё не выбрано | Независимая частота отображения снимков |

Моторная задержка по умолчанию — 40 мс, горизонт predictor — 100 мс.
Это параметры toy-эксперимента, не физиологические константы.
`render_fps` в Gymnasium — metadata; оно не доказывает, что приложение
выдерживает эту частоту по настенным часам. Headless training может идти
быстрее или медленнее реального времени, сохраняя тот же физический шаг.

CLI уже ограничивает темп по монотонным часам через `--realtime`, сохраняя
фиксированный физический шаг. При отставании он продолжает шаги без ожидания,
не увеличивая `dt`. Учёт missed deadlines и расписание интеграции с UE ещё
предстоит добавить; правило догоняющих шагов/замедления должно быть явным.
Нельзя молча пропускать физические шаги или сокращать моторную задержку ради FPS.

## Начальное распределение ресурсов одного ПК

| Компонент | Начальное решение | Что измерять |
| --- | --- | --- |
| MuJoCo и четыре мышцы | CPU | Время всех подшагов и неявных решений |
| Policy и predictor | CPU, batch 1 | Подготовку observation, inference и action mapping |
| Обмен состояниями | CPU, ограниченный буфер | Сериализацию, копии, ожидания и возраст снимка |
| UE | CPU-потоки и GPU | Game/Draw/RHI/GPU time, память и ожидания |
| Flesh / ML Deformer | Отдельный выбранный режим | CPU и GPU вклады каждого компонента |

Это исходное инженерное решение, не результат сравнения производительности.
Flesh/ML Deformer нельзя заранее записывать целиком в «свободную GPU»:
стоимость зависит от solver, threading, модели, ассета и backend.
Сначала измеряются skinning, затем отдельное добавление deformer и Flesh.
Основа: [Flesh overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/chaos-flesh-overview?application_version=5.7).

При будущем переносе inference в UE [NNE](https://dev.epicgames.com/documentation/en-us/unreal-engine/neural-network-engine-overview-in-unreal-engine)
предоставляет CPU, GPU и RDG-интерфейсы. CPU-входы и выходы не требуют обмена
с GPU. GPU-вариант с CPU-тензорами добавляет передачи и синхронизацию;
RDG работает с render-graph GPU-буферами. Выбор GPU проверяется полным временем
«observation → готовая CPU-команда», а не только временем вычисления сети.

Асинхронный [GPU readback](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/RHI/FRHIGPUMemoryReadback?lang=en-US)
использует staging buffer и fence. Позднее чтение может убрать немедленное
ожидание, но добавляет задержку; если MuJoCo уже ждёт именно этот action,
зависимость не исчезает. Экспорт модели в NNE и совпадение его результатов
с Python ещё предстоит реализовать и проверить на закреплённой версии UE.

## Владелец состояния и направление сообщений

Физический процесс единолично обновляет механику, задержки, activation,
упругие состояния и capacity. UE получает согласованный снимок завершённого
шага. Render thread не читает изменяемый state посередине интегрирования.
Эта граница согласуется с подходом [URLab snapshots](https://urlab-sim.github.io/UnrealRoboticsLab/concepts/architecture/),
но наш внешний процесс требует собственного адаптера.

Для изображения используется ограниченный канал последних снимков. Устаревшие
визуальные кадры можно заменить свежими; исследовательская запись хранит
пропуски явно. При остановке связи UE помечает картинку как stale; последняя
поза не считается новым физическим результатом. Интерполяция меняет только
отображение и сама добавляет настраиваемую задержку.

Будущие входящие команды несут номер, время и понятный момент применения.
Событие внешней силы должно быть применено один раз на физическом шаге.
Привязка часов, reset/episode identity, порядок мышц и метры→сантиметры
фиксируются на границе адаптера. Формат полей принадлежит отдельному
контракту телеметрии; здесь не вводится второй независимый wire protocol.

Возврат деформации Flesh в физику отсутствует в принятом плане. Если он
понадобится, это отдельное двустороннее сопряжение с проверкой задержки,
энергии и устойчивости. Нельзя одновременно запускать независимую физику
одной руки в MuJoCo и UE и считать расхождение чисто визуальным эффектом.

## Измеримый бюджет и критерий реального времени

Для одного control period стартовая оценка CPU-пути:

`T_observation + T_predictor + T_policy + sum(T_physics_substeps) + T_publish`.

Её сравнивают с 20 мс V0; при параллельных задачах измеряют критический путь
и ожидания. Среднее ниже 20 мс недостаточно: нужны p50/p95/p99, максимумы,
число пропущенных deadlines и запас на фоновые задачи. Рендеринг измеряется
отдельно; CPU и GPU времена нельзя просто складывать при их перекрытии.

Перед признанием демо работающим в реальном времени фиксируются:

1. Целевой ПК, ОС, версии, режим сборки, сцена, разрешение и число персонажей.
2. Заданные пределы control latency, возраста снимка и frame time; например,
   выбранные 60 FPS означали бы бюджет кадра 16.67 мс, а не гарантию результата.
3. Прогон после прогрева с физикой, policy, predictor и визуальными слоями вместе.
4. Отсутствие растущей очереди и дрейфа от настенных часов; все misses видимы.
5. Сохранение качества управления и физического шага под нагрузкой рендеринга.

Пороговые значения утверждаются по первым измерениям и записываются в отчёт.
Скорость чужой сцены, высокая средняя FPS или низкий общий CPU usage не
считаются проверкой этого бюджета. Один загруженный поток может быть узким местом.

В UE начинать с [`stat unit`, `stat gpu`, `stat unitgraph`](https://dev.epicgames.com/documentation/en-us/unreal-engine/stat-commands-in-unreal-engine),
затем использовать [Timing Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/timing-insights-in-unreal-engine)
для CPU/GPU tracks и ожиданий. Учитывать VSync/FPS cap и стоимость редактора.
Внешний Python-процесс измеряется отдельно: его внутренние вызовы автоматически
не появляются в UE trace. Сопоставление делается по времени и номерам снимков.

Обучение policy, обучение predictor и подготовка deformation caches выполняются
отдельными этапами. Они не должны незаметно конкурировать за ресурсы во время
приёмочного runtime-прогона. UI-индикация сохраняет разные шкалы activation,
силы в N, strain и capacity независимо от выбранного визуального качества.
