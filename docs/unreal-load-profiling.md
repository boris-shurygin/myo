# Осторожное профилирование UE на десктопе

После сообщения о полном зависании ПК 2026-11-08 добавлен отдельный
`scripts/profile_unreal.py`. Он не повышает нагрузку автоматически и не запускает
обучение. Для каждого опыта сохраняются параметры, JSONL с отсчётами,
engine/console logs и итоговый `summary.json` в `.cache/unreal/profiles/`.
Результаты конкретных опытов — в [validation.md](validation.md).

## Ограничения запуска

По умолчанию дерево UE запускается с affinity на два логических процессора,
приоритетом Below Normal и **6 GiB committed memory на весь Windows Job Object**.
Два логических процессора выбираются из текущей affinity mask; это не обязательно
два разных физических ядра. На i5-12400F первая проверенная маска — `0x3`.
Процесс создаётся приостановленным: сначала назначаются ограничения, затем
возобновляется выполнение. Если назначение Job Object невозможно, UE не запускается.
`-corelimit=2` дополнительно сообщает движку два ядра; в проверяемой ветке исходников
это выбирает один shader worker. Реальное число workers записывает монитор.

При закрытии последнего handle Job Object завершаются входящие в него процессы.
Внешний монитор также завершает дерево после бюджета времени или срабатывания
порога. Записывается число оставшихся процессов; чужие UE-процессы не завершаются.
Проверены небольшой дочерний процесс, наследование affinity, остановка его дерева
и отказ тестового выделения памяти сверх hard limit.

Внешние пороги начальных опытов:

| Условие остановки | Значение по умолчанию |
| --- | ---: |
| Остаток физической RAM | меньше 6 GiB |
| Доступный commit по GlobalMemoryStatusEx | меньше 6 GiB |
| Максимум private bytes дерева и peak job commit | больше 90% от лимита Job Object |
| Общая занятая VRAM | больше 8192 MiB |
| Температура GPU | 75 °C и выше |
| Промежуток между измерениями | больше 5 s |
| Время опыта | заданные `--seconds`, максимум 120 s |

Это выбранные инженерные бюджеты, не пределы оборудования. Hard limit Job Object
относится к committed memory, а не к working set или VRAM. При достижении лимита
приложение может получить ошибку выделения памяти. VRAM/температура контролируются
опросом `nvidia-smi`; жёсткого GPU-лимита нет. При полном зависании ОС или сбое
драйвера монитор тоже может не получить процессорное время. Отсутствие срабатывания
порогов не доказывает отсутствие такой причины зависания.

Ручная остановка: Ctrl+C в терминале монитора либо создание файла
`.cache/unreal/STOP_PROFILE`. Файл проверяется до запуска и на каждом отсчёте;
после ручной остановки его нужно удалить перед новой пробой.

## Порядок опытов

Из корня репозитория, в PowerShell:

```powershell
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage selftest
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage baseline --seconds 15
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage probe --seconds 45
```

Далее, по одному запуску с оценкой лога, измерений и отзывчивости рабочего стола:

```powershell
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage render-entry --seconds 45
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage render-entry --seconds 90
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage render-bones --seconds 90
```

Начальная графическая конфигурация: **DX11, offscreen, 640×360, 10 FPS**.
Это отдельная диагностическая конфигурация; прежний незавершившийся запуск
использовал DX12. Меняется только один параметр между соседними графическими
пробами: сначала длительность, затем сцена. Shader cache может прогреваться;
поэтому повторный запуск не является идентичным сравнением.

Остановка по времени означает завершение окна измерений, а не успешную загрузку
редактора. Готовность окна, рендера и сцены подтверждается отдельно по engine log
и кадру. Для оценки интерфейса offscreen-проба недостаточна.
Загруженная карта проверяется по `MAP LOAD FILE` в console log. При отсутствии
запрошенной карты опыт получает `target_not_loaded` даже при спокойных метриках:
первая проба костей действительно обнаружила такой сбой передачи аргументов.
Запуск без графики (`probe`) должен дополнительно завершить свой Python-скрипт
и вернуть exit0; `baseline` UE не создаёт.

При устойчивой работе можно менять отдельно `--fps 20`, затем разрешение
`--width 960 --height 540`. Увеличение CPU до `--cores 3` допускается отдельным
опытом, а не одновременно с разрешением/FPS. Готового автоматического sweep нет.
Симуляция Flesh начинается отдельной ступенью после работоспособного костного
рендера и устранения текущего blocker сохранённой Flesh collection.

## Просмотр сцены

Для просмотра подготовленной сцены **в отдельном окне без панелей редактора**:

```powershell
.\view-arm.cmd
.\view-arm.cmd -Pose 45 -Seconds 60
.\view-arm.cmd -View muscles
```

Используется установленный UE 5.8.4 в режиме `-game`. Это ещё не упакованный
самостоятельный `.exe`: нужны локальные UE, `.venv` и сгенерированные ресурсы.
Доступные позы: 15, 45, 90, 120°. Вид `muscles` добавляет шесть предварительно
подогнанных поверхностей BodyParts3D, см. [подготовку мышц](bodyparts3d.md).
Сейчас это статический скелет с грузом и необязательными поверхностями;
управление мышцами, live-физика и кожа в этом окне пока не реализованы.
Камера выбирается автоматически, освещение динамическое, пересборка света не нужна.
Управление после фокуса окна: мышь — поворот; WASD — перемещение;
Q/E или Ctrl/Space — вниз/вверх. Home возвращает исходный вид перезагрузкой
статической сцены; Esc закрывает окно. Скорость40 cm/s подходит масштабу руки.
Видимый шар навигатора удалён: у управляемого pawn нет меша, камера следует ему.
Синий шар возле кисти — условный груз MuJoCo, он остаётся частью сцены.
Окно работает при DX11, 640×360, cap20 FPS, двух логических CPU и лимите commit6 GiB.
По умолчанию через120 s монитор закроет окно; можно закрыть его раньше кнопкой
окна или остановить монитор через Ctrl+C. Лимиты ресурсов сохраняются.

Если ресурсы ещё не подготовлены, сначала выполните экспорт и ограниченный импорт:

```powershell
.\.venv\Scripts\python.exe -m myo.unreal_geometry
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage prepare-bones --seconds 120
```

Редакторский режим остаётся для разработки:

```powershell
.\.venv\Scripts\python.exe scripts/profile_unreal.py --stage render-bones --seconds 120 --fps 20 --visible
```

Он выбирает `UnrealEditor.exe`, убирает `-RenderOffscreen` и сохраняет ограничения.
Python-скрипт выбирает камеру и проверяет ссылки на все костные меши после загрузки.
Для диагностического кадра: `--stage render-bones --seconds 120 --fps 20 --capture-frame`.
Для кадра самого вьювера: `--stage viewer --seconds 45 --fps 20 --capture-frame`;
кадр снимается native CSV frame command после120 кадров прогрева и копируется
в каталог опыта. Снимок в первом кадре может содержать ещё не загруженные материалы.

## Метрики и их границы

CPU измеряется для всей системы через GetSystemTimes и отдельно для Job Object
(процент всей машины, а не одного ядра). RAM — доступная физическая память;
для дерева отдельно сохраняются private bytes, сумма working sets и peak commit.
Сумма working sets может повторно учитывать shared pages. GPU utilization,
температура, мощность и VRAM относятся ко всей видеокарте, включая другие приложения.
Это монитор ресурсов, не GPU frame profiler: GPU frame time, draw calls и
стоимость Flesh он не разделяет.

Новые зависимости не нужны: Win32 API через ctypes и установленный `nvidia-smi`.
Основа ограничений:
[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
[extended limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information).
Не следует заменять наблюдаемую отзывчивость предположением, что наличие лимитов
само по себе гарантирует устойчивость компьютера.
